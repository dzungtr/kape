# Title: Kubernetes Agentic Platform Execution (KAPE)

## Status
**Draft**

## Problem Statement
Modern Kubernetes clusters generate enormous volumes of signals -- security violations, resource pressure, policy breaches, cost anomalies, and runtime anomalies. Existing tooling either acts without reasoning (autoscalers, Kyverno enforcement, Falco alerts) or reasons without acting (K8sGPT), and nearly all require code changes to extend. No platform exists today that combines event-driven signal collection, LLM-powered contextual reasoning, declarative CRD-based configuration, a reusable skill library, and extensible MCP tool execution into a single Kubernetes-native system.

## Goals
- Provide a generic AI agent engine configurable entirely through Kubernetes CRDs, enabling GitOps-friendly management.
- Integrate natively with existing ecosystem tools (Falco, Cilium, Kyverno, Karpenter, Prometheus) as event sources via lightweight adapters.
- Support extensible tool execution via MCP servers -- engineers deploy MCP servers, KAPE consumes them via `KapeTool` CRDs without code changes.
- Maintain a full, immutable audit trail of all LLM decisions and actions via structured Task records persisted by `kape-task-service`.
- Enable independent per-handler scaling via KEDA on NATS JetStream consumer lag, including scale-to-zero for latency-tolerant handlers.

## Non-Goals
- KAPE is not a replacement for dedicated autoscalers (Karpenter, KEDA) or policy engines (Kyverno, OPA).
- IAC and Helm chart packaging for production deployment is out of scope for this spec.
- Multi-cluster topology management is not addressed in v1.

## User Stories
- As a platform engineer, I want to define an automated incident investigation pipeline as a single YAML CRD, so that I can add new agent behaviours without writing Go or Python code.
- As a security engineer, I want Falco alerts to trigger an LLM-driven investigation that checks Kubernetes context and PagerDuty on-call status before escalating, so that incident responses include relevant context and reduce false-positive pages.
- As an SRE, I want to reuse common investigation procedures (e.g. "check order lifecycle events") across multiple handlers via a skill library, so that best practices are shared consistently without duplication.
- As a compliance officer, I want every agent decision and action recorded in a structured, immutable audit trail, so that we can satisfy audit requirements and retroactively analyse incident response.
- As a cost engineer, I want Karpenter consolidation events to be analysed by an agent that runs only when events arrive (scale-to-zero), so that cost investigation logic incurs no ongoing resource cost.

## Functional Requirements
- FR-1: The operator MUST watch `KapeHandler`, `KapeTool`, `KapeSchema`, and `KapeSkill` CRDs and reconcile handler Deployment lifecycle (create, update, delete) in response to CRD changes.
- FR-2: Each `KapeHandler` CRD MUST result in exactly one Deployment whose pods contain a `kapehandler` (Python LangGraph agent) container and a `kapeproxy` (MCP federation sidecar) container.
- FR-3: The operator MUST materialize each `KapeHandler` spec and all referenced `KapeSkill` instructions into a ConfigMap mounted into the handler pod at a known path.
- FR-4: The `kapeproxy` sidecar MUST federate all upstream MCP servers referenced by `KapeTool` CRDs into a single localhost MCP endpoint, filtering tools by `KapeTool.spec.mcp.allowedTools` and namespacing them as `{kapetool-name}__{tool-name}`.
- FR-5: The operator MUST compute the union of tools from `KapeHandler.spec.tools[]` and all referenced `KapeSkill.spec.tools[]`, deduplicate by `KapeTool` name, and render a single `kapeproxy-config` ConfigMap.
- FR-6: The Kubernetes API server audit log MUST be routable through a `kape-audit-adapter` that normalizes audit events into CloudEvents and publishes them to NATS JetStream.
- FR-7: Falco alerts MUST be routable through a `kape-falco-adapter` (receiving from falco-sidekick) that normalizes events into CloudEvents and publishes them to NATS JetStream.
- FR-8: Prometheus/AlertManager alerts MUST be routable through a `kape-alertmanager-adapter` that normalizes events into CloudEvents and publishes them to NATS JetStream, with NATS subject configurable via a `kape_subject` label on the alert.
- FR-9: The event broker MUST be a NATS JetStream cluster with a single `KAPE_EVENTS` stream (subject filter `kape.events.>`), 24-hour retention, and replication factor 3, deployed as a 3-node StatefulSet with mTLS client certificates.
- FR-10: Each `KapeHandler` MUST have a corresponding KEDA `ScaledObject` generated by the operator from `KapeHandler.spec.scaling`, using the NATS JetStream scaler with consumer lag threshold.
- FR-11: The `kapehandler` runtime MUST always register a built-in `load_skill` tool that reads skill instructions from `/etc/kape/skills/{skill-name}.txt`, renders Jinja2 template variables against the current event context, and returns the resolved text to the agent.
- FR-12: The LLM output MUST be validated against the declared `KapeSchema` Pydantic model. Any schema validation failure MUST halt execution without executing actions and write a `Task{status: SchemaValidationFailed}` record.
- FR-13: Immutable Task audit records MUST be persisted via a Go REST API (`kape-task-service`) to PostgreSQL, capturing LLM input, reasoning steps, tool calls, actions taken, and output schema validation.
- FR-14: Handler-to-handler chaining MUST be supported via the event broker using an `event-emitter` action type in the handler pod.

## Technical Context

KAPE is a Kubernetes-native system spanning six major component groups. The **event producers** (Falco, Cilium, Kyverno, Karpenter, Kubernetes API server) emit signals through lightweight adapters that normalize output into the CloudEvents specification. These events flow into the **event bus** -- a NATS JetStream cluster (3-node StatefulSet, mTLS, single `KAPE_EVENTS` stream with 24h retention). The **Kape Operator** (built with controller-runtime) watches four CRD types (`KapeHandler`, `KapeTool`, `KapeSchema`, `KapeSkill`) and manages the lifecycle of handler Deployments, ConfigMaps, KEDA ScaledObjects, and vector DB provisioning. Each **handler pod** runs a `kapehandler` Python LangGraph ReAct agent and a `kapeproxy` MCP federation sidecar. Agent execution traces emit OTEL spans following Arize OpenInference conventions. The **kape-task-service** (Go REST API) persists immutable Task audit records to PostgreSQL, powering the **kape-dashboard** (live task monitor, timeout/retry management, agent trace view).

The system is designed as a single-operator architecture -- one operator instance manages all CRD types -- following the workload topology decision in `docs/adr/0002-handler-runtime-never-reads-crds.md` (runtime accesses CRD data only through materialized ConfigMaps, never the API) and `docs/adr/0004-kapeproxy-single-federation-sidecar.md` (one federation sidecar per pod replacing the previous per-tool `kapetool` sidecar model). Task identity uses ULIDs via `docs/adr/0011-ulid-ids-keyset-pagination.md`, and the tasks table uses monthly partitioning (`docs/adr/0012-tasks-table-monthly-partitions.md`).

## Design Tenets
- All agent behaviour must be configurable through Kubernetes CRDs -- no code changes required for new handlers, tools, schemas, or skills.
- Event data received in the user prompt is UNTRUSTED and must be isolated from system prompt content (prompt injection defence at the system prompt level).
- The operator must never be in the hot path of event processing -- once handler Deployments are created, events flow directly from the broker to handler pods without operator involvement.

## Open Questions
- What is the exact resource specification (CPU, memory) for the `kapeproxy` sidecar under realistic production loads?
- Should `KapeSchema` validation be implemented as a Pydantic model in the handler runtime, or is there a case for a separate schema validation service?
- What is the backup and disaster recovery strategy for the NATS JetStream stream data and the PostgreSQL task database?

## Future Considerations
- `KapePolicy` CRD (v2) for cross-handler guardrails and namespace-level constraints.
- Argo Workflows integration (v2) for complex DAG remediation and human-in-the-loop approval workflows using `KapeRemediationWorkflow` and `KapeApprovalWorkflow` CRDs.
- `KapeConfig` CRD (v2) for cluster-wide configuration.
- Fine-tuning pipeline using the Task audit log as a labelled dataset.
- Simulation mode for replaying historical events against new handler configurations.
